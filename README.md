# MatchClip AI — 羽毛球智能剪辑

使用本地球员姿态模型和音频瞬态生成回合候选，人工复核后剪辑比赛视频。**剪辑不依赖计分牌**，计分牌延迟或不显示不会决定切点。

## 当前流程

1. 在选定时间范围抽样校准底线主机位的球场几何，过滤不匹配的放大镜头。
2. 每秒分析 5 帧，YOLO11n-pose 检测两侧球员的姿态。远场另做局部检测，结合球场上的移动速度和相对躯干的手腕运动计算活动强度；画面顶部 22% 被遮蔽，不读取计分牌。
3. 分块解码音频，通过高频频谱变化提取声音事件。画面运动为必要条件，声音仅辅助；持续的强视觉活动也能独立产生候选。短暂检测缺失不会立刻截断，不再按「至少四拍」删除短回合。
4. 时间序列规则寻找活动起止并保留边界余量。全部自动结果标为「待复核」，显示遮挡、切镜、范围边界等原因。
5. 页面支持原视频定位、回合连播、调整起止秒数、拆分、合并、删除、补录漏检和标记复核；选择片段后可直接导出实际剪辑的 MP4，或下载 FFmpeg 脚本、JSON 项目。

比分和胜方默认为未知，不再用发球方、近远场位置或回合数量猜比分。A/B 是固定球员身份，不是球场近远侧。JSON 可提供人工确认的 `scoreBefore: {a, b}` 作为比分锚点；出现胜方未知的回合后，后续比分继续保持未知，直到新的锚点。页面目前只支持标记胜方，未接入 OCR 或自动比分对齐。

## 能力边界

- 这是**真实姿态模型 + 时间序列规则的第一版**，没有训练专门的羽毛球动作分类器，也没有接入羽毛球轨迹模型。`hit_visual`、持球、落地字段没有真实检测能力，保持 false，不能作为识别结果使用。
- 当前针对绿色球场、底线固定主机位的单打。其他场地、双打或大幅变动的机位未验证；找不到可用主镜头会明确报错。
- 走位、热身、同机位回放可能误判为回合，遮挡和轻动作可能漏检，首尾可能偏移。候选数量、保留占比和活动强度都不是识别准确率；声音候选数也不是真实拍数。
- 不承诺自动成片无需检查。建议先分析 5–10 分钟，复核候选并检查空隙中的漏检，再扩大范围。选择「已复核」筛选后点「全选」即可只导出已确认的片段；未选择时会导出全部候选，页面会提示包含待复核片段。
- 首次运行从 Ultralytics 的官方 Hugging Face 仓库下载姿态权重。模型和视频处理均在本机，无需 API Key；模型使用须遵循 [Ultralytics 许可说明](https://www.ultralytics.com/license)。

## 本地运行

需要先安装 Node.js 20+、Python 3.12，无需 DeepSeek 或其他大模型的 API Key。

### 一键启动（推荐）

macOS 在项目文件夹中双击 **`start.command`**；也可以在 macOS/Linux 的项目目录运行：

```bash
npm start
```

入口会在首次运行时创建 `.venv`、安装缺失的前后端依赖，随后同时启动前后端，等待本地 API 就绪并打开 `http://127.0.0.1:3000`。首次安装需要联网；姿态权重在首次分析时下载。保持启动终端打开，按 `Ctrl+C` 同时停止两个服务。端口 3000 或 8000 被占用时会报错，不会终止已有服务或切换到其他端口。

在页面中选择本地视频 → 填写分析范围 →「开始视觉分析」→ 复核、调整候选片段 →「导出剪辑视频」→「下载剪辑成品」。一键启动不包含网上找比赛、下载视频或自动视觉复核。

只检查环境、不安装依赖或启动服务：`npm start -- --check`。不自动打开浏览器：`npm start -- --no-open`。Mac 下载 ZIP 后若提示没有执行权限，先运行 `chmod +x start.command`。

默认使用 CPU；可显式选择设备，例如 Apple Silicon 上运行 `MATCHCLIP_DEVICE=mps npm start`，兼容 CUDA 的机器运行 `MATCHCLIP_DEVICE=cuda npm start`。遇到设备兼容问题时使用默认 CPU。

### 分开启动 / 手动安装

以下命令适用于 macOS/Linux：

```bash
npm install
python3.12 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
npm run backend
```

另开终端：

```bash
npm run dev
```

打开 `http://127.0.0.1:3000`，选择本地视频，填写分析范围（秒），点击「开始视觉分析」。后端默认监听 `127.0.0.1:8000`，Vite 代理 `/api`；两个进程都需运行。后端未连接时页面会给出启动提示，不生成模拟结果。

默认 CPU 推理，处理时间取决于视频长度和机器性能；可用 `MATCHCLIP_DEVICE=mps npm run backend` 或 `MATCHCLIP_DEVICE=cuda npm run backend` 显式选择兼容的设备，本次仅验证了 CPU。视频上传至本机后端，最大 4 GB；一次运行一个分析/导出任务，最多接收两个待处理的分析任务。分析和导出均可取消。

FFmpeg 由 `imageio-ffmpeg` 提供，直接导出不需要额外安装。下载的独立剪辑脚本则需要 PATH 中有 `ffmpeg`，使用方法：

```bash
bash process_highlights.sh '/path/to/original.mp4' '/path/to/highlights.mp4'
```

剪辑按时间顺序逐段精确转码、拼接，保留原音轨，不添加未经确认的比分字幕。JSON 导入会校验时间范围和重叠；旧版默认胜方/近远方数据会清除。导入项目使用脚本导出；直接 MP4 导出需要当前会话中的本地分析任务。

模型、上传的视频副本、分析 JSON 和成品存放在 `.matchclip/`，不会提交到 Git，也不会自动删除。关闭后端并保存所需成品后，可清理 `.matchclip/jobs/` 释放空间。`MATCHCLIP_DATA` 可修改数据目录。后端重启后需要重新分析以使用直接导出，已有 JSON 和剪辑脚本仍可使用。

## 命令行分析与验证

```bash
.venv/bin/python -m backend.analyze '/path/to/match.mp4' \
  --start 240 --end 900 --output '/path/to/analysis.json'
npm test
npm run test:backend
```

输出时间戳均为原视频的绝对秒数。测试覆盖无计分牌/无音频的视觉分段、音频单独不能触发、短回合、短暂遮挡、切镜、未知比分、旧项目迁移、输入校验和真实 FFmpeg 剪辑。测试通过代表这些行为符合约定，不代表在真实比赛上达到某个准确率。

2026-10-15 使用 BWF 翁泓阳对 Christo Popov 的视频试跑 04:00–15:00，得到 21 个自动候选；抽查发现热身和捡球两段误检，在页面删除后保留 19 个候选，其余尚未逐段确认。通过页面选取三段并导出 17.8 秒、1280×720 的 MP4，完整解码通过；26 项前端测试和 14 项后端测试通过，未运行构建。实测记录见 [pose-audio-validation.json](doc/pose-audio-validation.json)，不能据此宣称真实比赛识别准确率。

随后对整场视频的 04:30–73:00 进行分析（手动跳过已确认的开场热身），生成 118 个待复核候选，导出约 19 分 56 秒、720p/30fps、保留原声的 MP4。CPU 分析加导出用时约 9 分 14 秒，完整成品解码通过，首尾抽查未混入赛后集锦。118 是候选片段数，不是已确认得分数；整场尚未逐分标注评估。比赛视频、模型权重和本地任务文件不包含在源码中。

代码入口：`backend/analyze.py`（处理流程）、`backend/vision.py`（姿态）、`backend/temporal.py`（分段）、`backend/server.py`（本地任务 API）、`hooks/useMatchAnalysis.ts`（前端任务）、`hooks/useRallyEditor.ts`（人工复核）。旧浏览器音频服务仍保留用于历史测试，主界面已不调用它。
